Migrating from ajv

Your JSON Schemas stay as they are: schiva reads draft-04, draft-06, draft-07, 2019-09 and 2020-12, and passes the whole JSON-Schema-Test-Suite of each. What changes is the code around them, and this page goes through it.

Overview

  • No instance. ajv compiles through an Ajv object that holds options, formats and schemas. schiva compiles with a function, compileJsonSchema(schema, options), and the options go with each call.
  • Errors are returned. An ajv function returns true or false and leaves the errors in validate.errors. A schiva function returns the errors: messages by default, objects with errors: 'objects', or true/false with errors: false. Nothing is kept between calls.
  • Every error by default. ajv stops at the first error unless allErrors: true. schiva reports every error unless allErrors: false.
  • Strict. An unknown keyword throws when compiling, as in ajv's strict mode. Declare your own annotations with keywords, or ignore unknown keywords with strict: false.
  • The data is not changed unless you ask: useDefaults and removeAdditional and coerceTypes work as in ajv.

Side by side

const Ajv2020 = require('ajv/dist/2020');
const addFormats = require('ajv-formats');

const ajv = new Ajv2020({ allErrors: true });
addFormats(ajv);
ajv.addSchema(addressSchema, 'https://example.com/address.json');

const validate = ajv.compile(orderSchema);
if (!validate(order)) {
  console.log(validate.errors);
}
const { compileJsonSchema } = require('schiva');

// The draft comes from "$schema" (or the option draft: '2020-12').
const validate = compileJsonSchema(orderSchema, {
  formats: true,
  schemas: { 'https://example.com/address.json': addressSchema },
  errors: 'objects', // or leave it out for messages
});

const errors = validate(order);
if (errors.length > 0) {
  console.log(errors);
}

ajv ships copies of the meta-schemas; to check schemas against draft-07, as ajv.validateSchema():

const metaSchema = require('ajv/dist/refs/json-schema-draft-07.json');
const validateSchema = compileJsonSchema({ $ref: 'http://json-schema.org/draft-07/schema#' }, { schemas: [metaSchema] });
validateSchema({ type: 5 }); // ['type must be one of: array, boolean, ...', ...]

Errors

By default a schiva function returns messages that start with the path of the field, ready for logs and HTTP responses: 'lines[0].price must be at least 0'. For code that reads the errors, as with validate.errors, use errors: 'objects': 

const validate = compileJsonSchema(schema, { errors: 'objects' });
validate({ lines: [{ price: -1 }] });
// [{ path: ['lines', 0, 'price'], pointer: '/lines/0/price', keyword: 'minimum', params: { limit: 0 },
//    message: 'lines[0].price must be at least 0' }]

To show your own messages, or translate them (as with ajv-i18n or ajv-errors), build them from keyword and params.

schiva also checks idn-hostname and idn-email, and passes every optional format test of the JSON-Schema-Test-Suite (see Formats in the guide).

Several documents

Documents that $ref points to go in the option schemas, by URI or with their $id. To load them as ajv's compileAsync() does, use compileJsonSchemaAsync() with the same loadSchema function: it is called once for each document the schema reaches and schemas does not have. 

compileJsonSchema(orderSchema, { schemas: [addressSchema, countrySchema] }); // schemas with "$id"
await compileJsonSchemaAsync(orderSchema, { loadSchema }); // loads them

A reference that does not resolve throws when compiling. Each document is read in the draft its own $schema names, so a 2020-12 schema can reference draft-07 documents.

Standalone code

standaloneJsonSchema(schema, options) gives the source of a module to write to a file when building, as ajv's standaloneCode(). There is no instance to create, the options are those of compileJsonSchema() with format: 'commonjs' or 'esm', and the module needs nothing else, not even schiva. See Standalone code.

TypeScript

ajv types a validator with ajv.compile<T>(schema), which is a type guard. In schiva, compileJsonSchema<T>(schema, { errors: false }) is the type guard for T. ajv's JSONSchemaType<T>, which checks a schema against a type, has no counterpart; with the DSL, the type comes from the schema instead: type Order = Infer<typeof order>.

What schiva does not do

ajv featureIn schiva
Keywords that write generated code (addKeyword with code)Not supported: define them with validate, compile or macro. ajv-keywords transform and dynamicDefaults change the data, and select needs $data.
$data referencesNot supported: $data as a keyword throws. Careful: inside the value of const or enum, { "$data": "1/b" } is not rejected but read as a plain value, as the JSON Schema standard says. Check those comparisons in your code.
Asynchronous validation ($async schemas)$async throws (ignored with strict: false): validation is synchronous. Loading documents is supported, with compileJsonSchemaAsync().
JSON Type Definition (JTD, ajv/dist/jtd)Not supported.
errorMessage (ajv-errors)Throws, as an unknown keyword. Build messages from keyword and params of the error objects.
schemaPath in errorsNot given; errors have the path of the value, the keyword and its params.

Checklist

  1. Replace ajv.compile(schema) with compileJsonSchema(schema, options), compiled once, when the program starts.
  2. Pick the result: messages (default), errors: 'objects' in place of validate.errors, or errors: false for true/false.
  3. If you relied on ajv stopping at the first error, add allErrors: false.
  4. Move addSchema() documents to the option schemas, and ajv-formats to formats.
  5. Compile every schema once: an unknown or misspelled keyword throws, which shows what to change.
  6. Look for $data, which schiva does not do; useDefaults, removeAdditional and coerceTypes are the same options.
  7. Where error objects are read, map instancePath to pointer, and required and additionalProperties errors to their new paths.
